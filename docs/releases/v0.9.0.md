# SupportOps AI Platform v0.9.0

## Overview

SupportOps AI Platform v0.9.0 completes the repository's defined backend and AI systems engineering scope.

The release presents a production-minded support operations backend built around durable execution, controlled LLM orchestration, semantic retrieval, human approval, observability, deterministic evaluation, and explicit prompt-release governance.

Version `0.9.0` communicates that the architecture, interfaces, tests, documentation, and local execution path are mature enough for technical review and demonstration while intentionally stopping short of a stable public `1.0.0` API or a production-deployed maturity claim.

## Architecture highlights

- FastAPI provides the synchronous API boundary.
- PostgreSQL remains authoritative for tickets, AgentRuns, approval state, audit records, knowledge metadata, LLM invocations, tool calls, recommendations, citations, usage, and estimated cost.
- AgentRun remains the outer durable execution boundary for scheduling, leasing, retry, recovery, and completion.
- LangGraph provides bounded inner workflow orchestration with PostgreSQL-backed checkpoint continuity.
- Qdrant remains a rebuildable semantic-retrieval projection.
- Langfuse remains optional derived telemetry and is not an audit ledger, business-state authority, or prompt-release authority.
- Workspace scoping models data ownership boundaries but does not claim secure authenticated public multi-tenancy.

## Reliability highlights

- Ticket intake and initial AgentRun creation are committed atomically.
- Workers claim runnable work with `FOR UPDATE SKIP LOCKED`.
- Leases and fencing tokens protect durable ownership.
- Bounded retries and stale-ownership recovery support at-least-once processing.
- Idempotent application boundaries protect sensitive execution and persisted outcomes.
- Optional telemetry fails open and cannot block authoritative business processing.
- Qdrant projections can be rebuilt from PostgreSQL-owned knowledge state.
- Exactly-once workflow execution is not claimed.

## AI systems highlights

- All LLM calls pass through an application-owned Gateway.
- Mock and OpenAI providers share application-owned contracts.
- Structured Outputs constrain classification, tool-decision, and recommendation responses.
- Prompts are immutable, explicitly versioned repository artifacts.
- LLM invocations persist provider, model, prompt, token, latency, and estimated-cost provenance.
- Knowledge documents and versions are immutable.
- Deterministic chunking and stable citation hydration preserve retrieval traceability.
- Registered tools are bounded and read-only.
- Sensitive escalation requires durable human approval before execution.
- The platform does not autonomously resolve tickets or perform external write integrations.

## Evaluation outcome

Prompt version 1 remains the runtime default for `ticket-classification`.

Prompt version 2 exists as an immutable offline evaluation candidate created from documented failure analysis. The repository includes committed static paired fixtures, deterministic comparison, safety-first release gates, and an explicit decision artifact.

The recorded outcome is:

```text
outcome: inconclusive
run_status: incomplete
approved_for_runtime_adoption: false
separate_runtime_adoption_required: true
runtime_prompt_version: 1
candidate_prompt_version: 2
```

This result demonstrates working release governance:

- static evidence validates comparison, provenance, safety-gate, and decision behavior;
- static fixtures are not provider-backed outputs;
- no empirical provider-backed superiority is claimed;
- an inconclusive decision cannot authorize runtime adoption;
- any future adoption requires canonical provider-backed evidence, human review, and a separate runtime decision.

The release also includes deterministic regression evaluation, grounded recommendation evaluation, and RAGAS integration behind repository-owned evaluation boundaries.

## Running locally

The default local path uses mock LLM and embedding providers and does not require OpenAI or Langfuse credentials.

```powershell
uv sync --frozen --all-groups
Copy-Item .env.example .env
docker compose up -d
uv run alembic upgrade head
uv run supportops-index-knowledge ensure-collection
```

Start the API:

```powershell
uv run uvicorn supportops.api.main:app `
  --host 127.0.0.1 `
  --port 8000
```

Start the worker in a separate terminal:

```powershell
$env:SUPPORTOPS_WORKER_ID = "worker-local-1"
uv run supportops-worker
```

## Intentional scope boundaries

The following capabilities remain intentionally outside the current release boundary:

- authentication and authorization;
- secure public multi-tenant identity and membership management;
- frontend applications;
- cloud deployment and infrastructure as code;
- real Jira, ServiceNow, Slack, or email writes;
- scheduled or online evaluation;
- production feedback ingestion;
- canonical paid-provider prompt benchmarking;
- runtime adoption of prompt version 2;
- external RAGAS baselines;
- Langfuse datasets and experiments as operational workflows;
- cross-provider fallback and automatic model routing;
- Redis, Celery, Kafka, or SQS;
- general OpenTelemetry, Prometheus, and dashboard infrastructure.

These boundaries preserve the repository's focus on durable backend execution, AI control, evaluation governance, and explainable engineering trade-offs.
